## 1. 问题定义

### 1.1 背景

ICPC/CCPC 比赛通常在最后一小时封榜。封榜后，公开榜单隐藏新提交的判题结果，但有的榜单仍显示队伍在某道题上交了几次、什么时候交的。这些信息和封榜前的表现结合，可以推断隐藏提交里有没有 Accepted（AC）。

本项目用 XCPCIO 公开的历史赛事数据，训练一个根据当前公开榜单预测冻结格子 AC 概率的模型。

### 1.2 目标

对于队伍 \(i\)、题目 \(j\) 和当前时刻 \(t\)：

- \(t_f\)：封榜开始时刻。
- \(R_{ij}(t_f,t)\)：该队伍在封榜后、截至当前已经产生的该题提交。
- \(Y_{ij,t}\)：这些提交中是否至少有一次最终被判定为 AC。
- \(I_t\)：当前时刻公开可见的信息。

目标是估计 **P(Y = 1 | I_t)**，其中 **Y = 1 当且仅当已经产生的隐藏提交中至少有一次 AC**。标签使用这些提交最终确认的判题结果，不要求在观察时刻已经完成评测。

预测单位是 **team × problem × observation_time**。只有封榜前尚未 AC、截至当前有隐藏提交的格子进入预测集合。

`p_ac` 模型本身不预测：

- 队伍之后能否做出某道题
- 队伍之后是否还会提交
- 具体哪一次提交是 AC

最终排名由 `standings` 用 `p_ac` 做蒙特卡洛模拟得到。

### 1.3 原则

1. 输出是校准后的概率，不是 AC/WA 分类。
2. 输入只包含观察时刻场外观众在公开榜单上能看到的信息。
3. 历史比赛通过时间回放生成监督样本。
4. 先建立可复现的统计基线，再上机器学习模型。
5. 以跨比赛泛化能力评价模型。
6. 优先级：数据正确性 > 无泄漏回放 > 统计评估 > 特征工程 > 模型复杂度 > 用户界面。

## 2. 数据源与相关工作

### 2.1 数据源

- 历史数据仓库：https://github.com/xcpcio/board-data
- 数据格式文档：https://xcpcio.com/zh/guide/data-format
- 榜单集成文档：https://xcpcio.com/zh/guide/board
- ICPC CCS API：https://ccs-specs.icpc.io/2026-01/contest_api

每场比赛由三个 JSON 文件组成：

| 文件 | 内容 |
|---|---|
| `config.json` | 比赛时间、封榜时间、题目、罚时规则、奖牌规则 |
| `team.json` | 队伍 ID、名称、学校、分组等 |
| `run.json` | 提交队伍、题目、时间、判题结果，部分比赛还有语言、提交 ID |

实际数据和文档示例有出入：

- 成都站等比赛使用 `ACCEPTED`、`WRONG_ANSWER`、`RUNTIME_ERROR` 等状态，文档示例使用 `correct`、`incorrect`、`pending`。
- 队伍文件可能是数组加 `id` 字段，也可能是映射。
- `frozen_time` 有的以秒为单位（成都站 `3600`），有的以毫秒为单位（西安站 `3600000`）。
- 比赛开始和结束时间有秒和毫秒两种；提交时间戳的单位由配置声明。

所以配置时间和提交时间分别推断单位，见 `normalize.py`。

### 2.2 数据质量风险

XCPCIO 文档指出，部分 DOMjudge 外榜的提交记录是从公开 scoreboard 反推合成的，并非真实的逐次提交记录。本项目依赖提交次数、间隔和最后提交时间，这类比赛的时间序列不可信。

实现：`audit` 逐场检查数据质量，按 A/B/C/X 分档。疑似合成的比赛归入 C 档，不参与训练和评估。board-data 不说明数据来源，所以所有比赛都带 `provenance_unknown` 标记。

### 2.3 相关项目

- **[ICPC AutoAnalyst](https://github.com/icpc-live/autoanalyst)**：分析比赛事件，推测队伍正在做的题目，识别关键排名变化。思路相近，但没有隐藏 AC 概率预测和概率校准。
- **[xcpc-sight](https://github.com/JunjieCharles/xcpc-sight)**：队伍和选手 Rating、题目难度建模、比赛前瞻和复盘。可借鉴的做法是按队伍实力修正题目难度、使用通过者分布。
- **[ICPC Tools Resolver](https://tools.icpc.global/)**：封榜结果揭晓和可视化。

在检索范围内，没有找到针对本项目定义的隐藏 AC 概率预测器的开源实现。

## 3. 建模假设与检验结果

以下是实现前提出的假设，每条后面附检验结果，数字的出处见 [`results.md`](results.md)。

### H1：题目难度影响隐藏提交的 AC 概率

封榜前通过的人越多、尝试后通过的比例越高，题目通常越容易。但通过率同时受选手水平和选题的影响，所以要结合总 AC 数、尝试队伍数、强队通过率、首次 AC 时间和一次通过比例，区分“容易想出解法”和“容易一次写对”。

**结果：** `ability_gap`（题目过题队伍占比减去队伍排名百分位）和 `problem_solve_rate` 是 CatBoost 重要性的前两名。

### H2：Dirt 率反映一次提交成功的倾向

`dirt = wrong_before_ac / (wrong_before_ac + accepted)`，按题目和队伍分别计算。传统 Dirt 只统计最终 AC 的题目，忽略了一直没过的尝试，所以另算 `first_attempt_ac_rate = first_attempt_accepted / all_first_attempts`，分母包含首次尝试未过的情况。尝试数少时用 Beta 先验平滑。

**结果：** 从完整模型里去掉 Dirt 率和首次通过率这一族，Brier 变差 0.0006，显著。

### H3：封榜前罚时能体现提交正确性

把总罚时分解为 AC 时间总和、计罚错误次数、每题平均错误次数等。

**结果：** 其他特征都在时，罚时分解没有可测的价值（去掉后 Brier 变化 −0.0002，不显著）。

### H4：封榜后同题再次提交是负面证据

队伍知道自己的判题结果，再次提交同一道题，通常说明之前的提交没有 AC。例外包括评测没完成就重交、同时交不同实现、AC 后仍然提交。

**结果：** 被拒后 10 分钟内重交同一题的比例是 51%，AC 后只有 1.6%。

### H5：最后一次提交后的沉默时间有预测价值

交完以后一直没有再交，可能是已经 AC 转去做别的题，也可能是没过但放弃了。要结合剩余时间、队伍能力和其他题目的提交行为判断。

**结果：** 沉默时长这一族显著（去掉后 Brier 变差 0.0006）。沉默 20 分钟以上的格子，AC 比例是 51%。专门的生存模型没有实现，沉默时长直接作为 CatBoost 特征。

### H6：同一队伍不同题目之间存在行为关联

一支队伍对 H 提交后持续在 J 上提交，可能说明 H 已经 AC，也可能是 H 被暂时放弃。

**结果：** 同队其他题目的活动显著（去掉后 Brier 变差 0.0004）。

## 4. 特征

所有特征都从观察时刻的公开快照计算，实际的特征列表和分组以 `features.py` 的 `GROUPS` 为准。消融实验按下面的分组逐级累加：

| 级别 | 新增的特征 |
|---|---|
| M1 | 题目通过率、队伍过题数 |
| M2 | Dirt 率和首次通过率、罚时分解、该格封榜前的提交历史 |
| M3 | 隐藏提交次数 |
| M4 | 隐藏提交的时间、间隔、沉默时长 |
| M5 | 同队其他题目的活动 |
| M6 | 转去做的题目难度、同题其他队伍的行为、封榜前一小时的题目趋势、距奖牌线的距离、队伍分组、最后几分钟的提交 |
| M7 | 比赛类型和比赛结构（题目区分度、过题数离散度、零题队比例等） |

比例类特征同时保留原始计数和平滑后的比例，平滑用强度为 3 的 Beta 先验。需要隐藏提交时间的特征在 Mode B 下是缺失值。

## 5. 数据处理与回放

### 5.1 归一化

`normalize.py` 把每场比赛转成统一的 `Contest`、`Team`、`Submission`，时间统一为相对开赛的毫秒数。处理的格式差异包括：

- 秒和毫秒两种时间单位
- 不同形式的 `frozen_time`
- 两套判题状态词表
- 数组和映射两种队伍列表
- 字符串和数字两种 ID

判题状态映射为四类：AC、计罚的错误、不计罚的错误（如编译错误）、未判定。不认识的状态报错。单位无法确定时抛出 `NormalizationError`，审计把这场比赛归入 X 档。没有封榜的比赛按最后 20% 的时间模拟封榜，并做标记。

### 5.2 公开快照

`replay.make_snapshot` 从完整记录生成观察时刻的 `PublicSnapshot`，其中包括：

- 封榜前提交的公开结果；封榜前的编译错误不显示
- 截至观察时刻的隐藏提交：Mode A 带时间，Mode B 只有次数；隐藏提交没有结果字段

`extract_features` 只接受 `PublicSnapshot`。标签由 `labels.py` 从完整记录单独生成。

### 5.3 观察时刻

每场比赛在封榜后 7 个时刻各回放一次：封榜时长的 1/12、2/12、4/12、6/12、8/12、10/12 和比赛结束。300 分钟、240 分钟封榜的比赛，就是第 245、250、260、270、280、290、300 分钟。样本键是 `contest_id + team_id + problem_id + observation_time`。

### 5.4 标签

对一个冻结格子：

- `y=1`：至少有一条封榜后、观察时刻之前的提交最终 AC。
- `y=0`：截至观察时刻的隐藏提交里没有 AC。

| 时间 | 真实记录 | 260 分钟可见 | 290 分钟可见 |
|---|---|---|---|
| 250 | WA | Pending | Pending |
| 280 | AC | 尚未产生 | Pending |

这个格子在 260 分钟的标签是 0，在 290 分钟的标签是 1。截至观察时刻仍有未判定提交的格子，从数据集中删除。

### 5.5 数据检查

`audit` 实现了以下检查：

- 提交时间超出比赛区间
- 引用不存在的队伍或题目
- 同一份日志在不同 ID 下重复发布
- 时间单位与比赛时长不一致
- 封榜后提交最终没有判定结果
- 疑似合成的时间序列：被拒提交时间为 0、同一格子时间完全相同、封榜后没有被拒提交
- AC 后又同题提交的比例

board-data 没有官方封榜榜单，所以重建的过题数、罚时和排名无法和独立来源对照。评测完成时间也没有记录，回放时无法还原当时还在评测队列中的提交。

## 6. 模型

- **M0 经验分组概率**：按“隐藏提交次数 × 封榜前是否尝试过 × 队伍排名段 × 题目通过率段 × 距最后一次提交的时间”分桶统计 AC 频率，并逐层向更粗的分桶收缩。
- **Logistic 回归**：全部特征，依次做中位数填补（附缺失指示列）、带符号的 log1p 变换和标准化。
- **CatBoost**：主模型，输入全部特征。
- **概率校准**：Platt 或保序回归，校准器只在验证比赛上拟合。实验流程在验证集上做两折交叉拟合来选校准方法；`train` 在训练比赛的 5 折样本外预测上拟合 Platt。

---

## 7. 评估

- **划分**：按整场比赛划分。按开赛时间，最近 20% 的比赛作测试集，之前 15% 作验证集，其余作训练集。消融实验和比赛类型研究用按比赛分组的 5 折交叉验证。
- **指标**：主要看 Brier、Log loss 和可靠性（分桶的预测概率与实际 AC 比例），辅以 ROC AUC、PR AUC 和按比赛平均的指标，避免大型比赛主导结论。
- **统计可信度**：模型之间的差异用按比赛重抽样的 bootstrap 估计置信区间。
- **分组分析**：按隐藏提交次数、封榜前尝试情况、题目难度、队伍强弱、沉默时长和观察时刻分组报告，见 `evaluation_report.md`。

同一格子在多个观察时刻各出现一次，训练时每个样本权重相同。比赛类型研究比较过让每场比赛权重相同，没有显著差别。

## 8. 推理接口

### 8.1 输入

输入是一份公开快照 JSON，包括：

- 比赛时长、封榜时刻、观察时刻
- 题目列表
- 封榜前的提交和公开结果
- 封榜后的隐藏提交：每次的时间，或者每格的次数
- 可选的队伍分组和奖牌规则

格式见 [`usage.md`](usage.md)。

### 8.2 信息可见性等级

| 模式 | 公开榜单能看到的 | 处理方式 |
|---|---|---|
| A | 隐藏提交的次数和时间 | 完整模型 |
| B | 每个格子的隐藏提交次数 | 不用时间类特征的模型 |
| C | 封榜后榜单停止更新 | 看不到新提交，不做预测 |

board-data 没有记录每场比赛实际用的是哪种展示方式。

### 8.3 输出

每个冻结格子输出：

| 字段 | 含义 |
|---|---|
| `contest_id` | 比赛 ID |
| `team_id` | 队伍 ID |
| `problem_id` | 题目 ID |
| `observation_time` | 观察时刻 |
| `hidden_submissions` | 观察到的隐藏提交次数 |
| `p_ac` | 至少一次 AC 的概率 |
| `model_version` | 模型版本 |
| `feature_version` | 特征版本 |
| `quality_flags` | 数据质量标记 |

### 8.4 概率不单调

“已经出现至少一次 AC”这个事件是单调的，新增提交不会让之前的 AC 消失。但模型的后验概率不单调：原本认为 250 分钟的提交可能 AC，到 280 分钟同一题又出现提交，反而说明前一次多半没过。

## 11. 调查问题与结论

1. **XCPCIO 历史比赛中，有多少场具有真实逐次提交日志？** 472 场中，A/B 档的正式赛有 164 场；162 场疑似合成（C 档），54 场无法使用（X 档）。
2. **每场比赛能生成多少冻结格子和样本？** 比赛结束时，每场的冻结格子中位数是 436 个；7 个观察时刻合计，平均每场约 2000 个样本。
3. **公开冻结榜单实际能看到哪些时间信息？** 数据里没有记录，所以 Mode A 和 Mode B 都做了建模。
4. **提交时间是否经过量化、截断或合成？** 有 122 场的时间只精确到分钟，其中 56 场没有合成迹象，归入 B 档，这 56 场里有 43 场是正式赛，用于训练。另有 162 场疑似由榜单合成，归入 C 档。
5. **真实日志中 AC 后重复提交的比例是多少？** AC 后 10 分钟内再交同一题的只有 1.6%；在已过的格子里，首次 AC 之后还有提交的比例，各场中位数是 1.7%。
6. **相邻提交间隔和前一次结果的关联有多强？** 很强：被拒后 10 分钟内重交 51%，AC 后 1.6%。
7. **Dirt 率是否有稳定的预测价值？** 有，但幅度小，见 H2。
8. **没有再提交的队伍，能否区分已经 AC 和放弃？** 部分可以。沉默时长和同队其他题目的活动都有显著贡献；沉默 20 分钟以上的格子，AC 比例 51%，模型平均给出 0.50。
9. **不同赛站和赛季之间是否有明显的分布漂移？** 没有直接测量。测试集是时间上最新的 33 场（2025-11-16 起），CatBoost 每场都优于 M0；只用同类比赛训练反而比用全部类型训练差。
